\section{Assignment 1: Histogram}

\subsection{Q1. Histogram Analysis for \texttt{id} and \texttt{title} Columns of \texttt{title} Table}

\subsubsection{1. Corresponding SQL Query}
to see what all colums needed form `pg\_stats'

\begin{lstlisting}[language=sql]
\d pg_stats;
\end{lstlisting}

to see histogram boundary values and other relevent  stored in \texttt{pg\_stats}:

\begin{lstlisting}[language=sql]
SELECT 
    attname, 
    null_frac, 
    n_distinct, 
    most_common_vals, 
    most_common_freqs, 
    histogram_bounds 
FROM pg_stats
WHERE tablename = 'title' 
  AND attname IN ('id', 'title');
\end{lstlisting}


\subsubsection{2. Kind of Histogram}
psql uses an equi depth histogram , where bucket bounderies are as such so that roughly the same number of tuples in each bucket


\subsubsection{3. Number of Buckets}
\begin{itemize}
\item Column \texttt{id}: \textbf{100 buckets} (101 bucket boundary values)
\item Column \texttt{title}: \textbf{100 buckets} (101 bucket boundary values)
\item extra -  to see the defualt number of buckets
\end{itemize}
\begin{lstlisting}[language=sql]
SHOW default_statistics_target;
\end{lstlisting}


\subsubsection{4. How Textual Attribute \texttt{title} is Put into Histogram}
textual attribute “title” is put into histogram as:

1. sorting the text strings in lexicographical order like bannana and apple will be apple, bannana after sorting

2. Sampling string values from the table like table title has around 2.5M rows , it will only sample around 30K

3. Encoding initial string prefix bytes into floating point numbers in $[0.0, 1.0]$ range for quantitative interpolation like laptop will be broken to lap with l = 108, a=97, p=112 then by 256 as between 0 and 1 , lap will be around 0.42 , we can then see where a key belongs between two keeys

4. Selecting quantile boundary string values at equal percentile intervals to form the 100 equi-depth bucket boundaries stored in \texttt{pg\_stats.histogram\_bounds}.

\subsubsection{7. Max Selectivity Error}
\begin{itemize}
\item \textbf{Max Selectivity Error}: Since \texttt{default\_statistics\_target} is 100, there are 100 buckets. Therefore, the maximum selectivity error for a range query is bounded by:
\end{itemize}
\[ \text{Max Error} \le \frac{1}{B} = \frac{1}{100} = 0.01 \quad (1.0\%) \]

For evaluated queries(q9), the observed maximum selectivity error is \textbf{0.8592\%} (0.008592), which strictly satisfies $\text{Max Error} \le 1.0\%$.

\subsubsection{8: Selectivity Estimation for Text Columns}
To estimate selectivity for a range query on a text column like title, psql first looks at the histogrambounds array in pgstats to figure out which bucket contains the query string, once it finds the target bucket, it counts all the full buckets that come before it. since it uses an equidepth histogram, each full bucket represents a fixed fraction of the total rows.   For the specific bucket where the string actually falls, psql assumes the data is uniformly distributed and uses linear interpolation. It converts the first few bytes of the strings into floating point numbers between 0 and 1. This allows it to calculate the mathematical fraction of exactly where the query string sits between the buckets minimum and maximum boundaries. finally it adds this fractional piece to the sum of the preceding full buckets to get the final overall selectivity estimate

\[ T(N) = m \cdot N + c \]

\begin{itemize}
\item Point 1: $(N_1, T_1) = (1000, 0.0006)$

\item Point 3: $(N_3, T_3) = (5000, 0.0029)$

\begin{itemize}
\item $\bar{N} = \frac{1000 + 3000 + 5000}{3} = \mathbf{3000}$

\subsection{9: The Trade-off of Bucket Counts}
Picking the number of buckets B is basically a trade off between how fast the histogram builds and how accurate the query planners estimates are.  If we use a small number of buckets, the DP algo runs much faster since its time complexity is O(B*N\textasciicircum{}2). It also saves memory in the system catalog and keeps query planning times short. The major downside is that wide buckets lead to higher selectivity errors. The database has to assume the data is uniformly distributed inside those large buckets, which usually isnt true and causes the estimates to lose resolution.  On the other hand using more buckets gives the optimizer a highdefinition picture of the actual data distribution, significantly dropping the max selectivity error. The catch is that computing these optimal partitions takes considerably more CPU time, uses more storage space, and adds overhead during the query planning phase before execution can begin.
