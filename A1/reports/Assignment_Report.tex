\subsection{1. Histogram Analysis for `id` and `title` Columns of `title` Table}

\subsubsection{. Corresponding SQL Query}
to see what all colums needed form `pg\_stats'

\begin{lstlisting}

\end{lstlisting}
to see histogram boundary values and other relevent  stored in \texttt{pg\_stats}:

\begin{lstlisting}
SELECT 
    attname, 
    null_frac, 
    n_distinct, 
    most_common_vals, 
    most_common_freqs, 
    histogram_bounds 
FROM pg_stats
WHERE tablename = 'title' 
  AND attname IN ('id', 'title');
\end{lstlisting}

\subsubsection{. Kind of Histogram}
PSQL uses an Equi Depth Histogram combined with a Most Common Values list. In an equidepth histogram, all buckets contain approximately the same number of rows ($approx N / B$), while bucket boundaries vary in width according to data distribution.


\subsubsection{. Number of Buckets}
\begin{itemize}
\item Column \texttt{id}: \textbf{100 buckets} (101 bucket boundary values)
\item Column \texttt{title}: \textbf{100 buckets} (101 bucket boundary values)
\item extra -  to see the defualt
\begin{lstlisting}
SHOW default_statistics_target;
\end{lstlisting}
\end{itemize}
\subsubsection{. How Textual Attribute `title` is Put into Histogram}
Textual attributes in PostgreSQL are converted into histograms by:

1. sorting the text strings in lexicographical order like bannana and apple will be apple, bannana after sorting

2. Sampling string values from the table like table title has around 2.5M rows , it will only sample around 30K

3. Encoding initial string prefix bytes into floating-point numbers in $[0.0, 1.0]$ range for quantitative interpolation like laptop will be broken to lap with l = 108, a=97, p=112 then by 256 as between 0 and 1 , lap will be around 0.42 , we can then see where a key belongs between two keeys

4. Selecting quantile boundary string values at equal percentile intervals to form the 100 equi-depth bucket boundaries stored in \texttt{pg\_stats.histogram\_bounds}.

\subsubsection{. Max Selectivity Error}
\begin{itemize}
\item \textbf{Max Selectivity Error}: Since \texttt{default\_statistics\_target} is 100, there are 100 buckets. Therefore, the maximum selectivity error for a range query is bounded by:
\end{itemize}

$$\text{Max Error} \le \frac{1}{B} = \frac{1}{100} = 0.01 \quad (1.0\%)$$


For evaluated queries(q9), the observed maximum selectivity error is \textbf{0.8364\%} (0.008364), which strictly satisfies $\text{Max Error} \le 1.0\%$.



\subsubsection{: Selectivity Estimation for Text Columns}

Selectivity estimate is done for range query on text column such as “title” in PSQL such as:


\begin{itemize}
\item \textbf{Bucket Identification:} The engine scans the \texttt{histogram\_bounds} array stored under pg\_stats to locate the specific bucket where the target string (\texttt{'Race'})  is
\item \textbf{Full Bucket Summation:} It counts all complete buckets preceding the target bucket. Each full bucket represents a fixed fraction of total rows (1/B).
\item \textbf{Text-to-Numeric Conversion:} For the target bucket, PostgreSQL converts initial string bytes into floating-point numbers in $[0.0, 1.0]$ range for interpolation as explain in part 4
\item \textbf{Linear Interpolation:} Assuming uniform distribution inside the target bucket, it calculates the target's position using:
\end{itemize}

$$\text{Fraction} = \frac{\text{Query Value} - \text{Bucket Min}}{\text{Bucket Max} - \text{Bucket Min}}$$


\begin{itemize}
\item   Final Calculation is done by adding the fractional bucket estimate to the sum of preceding full buckets to get the final estimated selectivity.
\end{itemize}

\subsubsection{. Impact of Bucket Count ($B$) Choice}
\begin{itemize}
\item \textbf{Fewer Buckets (e.g., $B = 5$ or $10$)}:
\item \textbf{Pros}: Lower memory footprint in system catalog, faster histogram build time ($O(B \cdot N^2)$ decreases), faster query optimization time.
\item \textbf{Cons}: Coarser resolution, leading to higher selectivity estimation errors, especially for skewed or non-uniform data distributions.
\item \textbf{More Buckets (e.g., $B = 50$ or $100$)}:
\item \textbf{Pros}: Finer granularity, significantly lower selectivity estimation error, highly accurate cost estimation for complex query joins.
\item \textbf{Cons}: Higher histogram construction time, larger storage overhead in catalog, and slightly higher plan generation latency during query execution.
\end{itemize}
